## Sprintmål
När sprinten är avslutad ska kaféets startsida vara en enkel och användarvänlig landningssida där besökaren kan ta del av viktig information om kaféet. Detta inkluderar öppettider, dagens kaka, kaffe priser, kontaktuppgifter, allergianpassade alternativ (exempelvis nötfria produkter), vegetariskt alternativ, wifi och lösenord, kundkort, erbjudanden, betalningsmöjligheter, rullstolsanpassning samt information om uteserveringen, events och parkering.

## Retrospektiv
**- Start:** Vi vill börja ha tydligare tider för möten och genomföra kodgranskningar direkt efter att en Pull Request skapats. Vi vill även bli bättre på att uppdatera sprinttavlan löpande och kommunicera tidigt om någon stöter på problem med Git eller merge-konflikter.

**- Stop:** Vi vill sluta vänta för länge med att uppdatera tavlan eftersom det gjorde det svårare att få en tydlig överblick över projektets status. Den största utmaningen under sprinten var att hitta tider som passade hela gruppen, vilket vi vill göra enklare framöver genom bättre planering.

**- Continue:** Vi vill fortsätta använda Pull Requests för alla ändringar eftersom det gav en tydlig historik över arbetet och skapade ett bra arbetsflöde. Vi vill även fortsätta med dagliga standups och vår aktiva kommunikation via Discord, eftersom det hjälpte oss att hålla oss synkroniserade, stötta varandra och snabbt lösa problem som uppstod.

**- Konkret förbättring:** Nästa sprint ska varje Pull Request granskas och godkännas samma dag som den skapas för att undvika flaskhalsar. Vi vill även använda ett mer specialiserat verktyg för sprintplanering och uppföljning, till exempel Trello eller Jira, för att göra sprinttavlan tydligare och enklare att underhålla.

## Teorifrågor
1. Vad är agil utveckling, och vad i ert arbetssätt den här veckan var agilt?
Agil utveckling innebär att man arbetar iterativt i mindre steg där man kontinuerligt planerar, genomför, utvärderar och förbättrar arbetet. Under denna sprint arbetade vi agilt genom att använda Scrum, hålla dagliga standups, arbeta med en sprintplan och leverera funktioner stegvis via Pull Requests.

2. Vilka Scrum-roller och moment använde ni (till exempel Scrum Master, daily, sprint och retrospektiv)? Beskriv hur de fungerade i er grupp.
Vi använde rollen Scrum Master som ansvarade för att leda planering, daily standups och hålla tavlan uppdaterad. Gruppen arbetade i en sprint under veckan och genomförde dagliga avstämningar samt ett retrospektiv. Dessa moment hjälpte oss att följa upp arbetet och identifiera eventuella hinder.

3. Beskriv hur en user story gick från Att göra till Klart hos er, med branch, Pull Request, review och merge.
När arbetet började flyttades kortet från "Att göra" till "Pågår". Utvecklaren skapade sedan en egen branch från main och implementerade sin user story. Därefter skapades en Pull Request på GitHub som granskades och godkändes av en annan gruppmedlem. Efter godkännandet mergades Pull Requesten till main och kortet flyttades till "Klart".

4. Vad är en merge-konflikt, när uppstår den och hur löser man den på GitHub?
En merge-konflikt uppstår när två personer ändrar samma del av en fil och Git inte kan avgöra vilken version som ska användas. Konflikten löses genom att jämföra de olika ändringarna och välja eller kombinera den korrekta versionen innan merge genomförs. Ett exempel kan vara om två personer samtidigt ändrar samma funktion i index.html.
